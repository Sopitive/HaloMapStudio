Film data

A Halo: Reach saved film is a recording of the game’s network traffic, and Halo Map Studio can read nearly everything in it as data: every object and where it was, the Forge labels and zones of the map the match was played on, who stood inside what and when, the gametype’s Megalo variables, kills and other events, who held which seat, and the score. This page is the guide to getting that data out — as CSV or JSON from the script system, or streamed as it happens from a match that is still being recorded — for whatever you want to build: stats overlays, timers, objective trackers, kill feeds, dashboards.

Reach only. Films from other titles are not read. Playback, cameras and the in-app statistics panel are on the Theater page; this page is only about extracting data.

What a recording contains

The film is a time line of ticks (60 per second, from 0 at the start of the recording). Everything below is addressed by tick; every verb prints both tick and seconds.

Kind of dataWhat you getVerb
Roster and seatsWho held each of the 16 player slots and when: joins, leaves, swaps, team changes, with the player’s name and identifier. A slot can be held by different people over a match, so everything keyed by slot should be read through the seats.film seats
Entity tracks (objects)Every object the game replicated: bipeds, vehicles, weapons, items, generic objects, devices. For each: its type, the tick it was created and (if it was) destroyed, its position and orientation whenever they were sent, the object it is attached to (parent), and — for player bodies — which player owns it.film objects, film object
Replicated multiplayer propertiesPer object: a flag word, a team, and a boundary shape (sphere, cylinder or box) with its size. This is how zones (flag bases, hills, goal areas, kill volumes) are described in the stream.the mp_* columns of film objects; film inside
Forge label and spawn dataThe label text, spawn sequence, respawn time, team, colour and placement flags of the Forge object an entity came from. These are not in the stream; they come from the map variant the film embeds in full, and HMS joins each entity to its placement by position (see limits).the label and placement_*/placed_* columns
Events and incidentsThe game’s 72-type event channel on the tick line: kills and medals (incident), weapon fire, reloads, pickups, vehicle entry and exit, melee, grenade throws, and so on.film events
ScoreboardThe change log of each player’s and each team’s round score, total score and rounds won.film score
Megalo variablesFor a scripted gametype: the global, player and team variables the game replicated, as time series, plus the round clock and game state. Declarations (which variables exist and how they are replicated) are read from the embedded gametype.film megalo
Gametype settingsTitle, author, engine type, team/round/respawn settings, and the Megalo declaration summary.film variant

The Megalo variables a recording carries are those the engine sends over the network: variables whose network priority is low or high (player.number[n], player.timer[n], team.object[n], global.number[n], …), plus the round clock, the current round and the game-finished flag. Each is a series of changes: a value holds until the next change. Player variables are keyed by player slot; the output also names whoever held that slot at that moment. Timers are reported as seconds left (with the engine’s rate code and an at-edge flag). Object variables (a team’s flag, say) hold object references that match an entity in the recording.

What is not in a recording

  • Megalo variables with network priority none or local are never sent. If the script never put a value in a replicated variable, no film has it.
  • Per-object Megalo variables (object.number[n] etc.). The engine has no replication codec for them that HMS could find. They are listed as declared by film megalo decls but never have values.
  • Variable names. A gametype stores no names; a variable is only scope.kind[n]. What player.number[2] means is up to the script.
  • A variable’s value before its first update. A film starting mid-match carries a variable only from the moment it changes.
  • Forge label, spawn sequence, respawn time and colour for objects the gametype spawned at runtime. They have no placement in the variant, so they have no label.
  • The match’s kill feed. The kill and medal feed is personal in Reach: the recording names the kills of the player who saved the clip, not everyone’s. Other deaths are seen as a body being destroyed, sometimes with a responsible unit; the full story is not there.
  • Which loadout a player chose (player-side state, never transmitted) and anything that is purely a client-side effect.
  • Positions on every tick. A body’s position is sent on some ticks only; HMS holds the last sample until the next one. Small zones can be crossed between two samples.
  • Tag names without a map. An object’s definition is a network tag reference; turning it into a tag path needs a map cache (--map to --film-follow). The script verbs print an empty tag column.

Getting started

There are three ways to run film queries. They all read the same data and print the same columns.

RouteNeedsUse it for
Script file or --exec — hms-app --script q.hscrThe app executable. The headless script host creates a graphics device first, so a GPU adapter (or the software rasteriser, see GPU notes) must be available. Nothing is drawn.One-off extraction and batch jobs over finished films. Output goes to stderr.
Running app — script console, or the TCP command server on 127.0.0.1:47800The GUI running (HMS_CMD_PORT changes the port; 0 disables the server).Querying a film you already have open, and driving it from another program. See Ways to run a script for the framing, and examples/hms_cmd.py for a ready-made client.
hms-app --film-followNothing else. No window, no GPU device, no audio.A match in progress (a growing .temp), servers, SSH, background jobs. See below.

Open the film, then index it

Every query is a film verb run after a film is open. The minimum is:

# q.hscr
film /path/to/match.mov
film index
echo @@begin
film objects label=zone_a
echo @@end
hms-app --script q.hscr 2>q.log
sed -n '/^@@begin$/,/^@@end$/p' q.log | sed '1d;$d' > objects.csv
  • film <path> opens a .mov, a .film or a .temp (the file MCC is writing while you play). It reads the header only and prints the film’s metadata. The line grammar has no quoting, so a path with spaces does not work; copy the film to a simple path.
  • film index decodes the recording. objects, object, inside, near, events, seats, score and dump need it first. film megalo and film variant read the file themselves and work without it. In a headless script film index finishes before the next line runs. In the running app it starts decoding on a worker thread and returns at once; until it finishes, the data verbs answer the recording is not decoded yet (film index, then wait), so retry (the example client does).
  • The headless log is the concatenated output of every command on stderr, with film <path> and film index adding their own text. Bracket a query with echo markers as above, or keep one query per script. Over TCP the response contains only the output of what you sent.
  • --exec joins its arguments with spaces into one line; to give several commands, put newlines inside one quoted string, or use --script.
  • MCC’s in-progress recording is a .temp in the Temporary\HaloReach\autosave folder of the MCC local data (File ▸ Open saved film… lists every folder it found); finished films are .mov in Movie folders. See Where films live. A .temp can be queried like a film, but is a snapshot of whatever had been written when it was read.

TopicRule
Time argumentsSeconds 12.5 (or 12.5s), mm:ss 1:30, or ticks t1234 (tick1234 also works). 60 ticks per second. Used by from=, to=, alive=, at=, film megalo at, film inside / near and --since. (film seek, the playback verb, takes plain seconds only.)
Time rangesa..b with each end in any of the forms above, e.g. 1:00..2:30 or t23000..t24100.
Object idsPrinted in decimal (id) and hex (id_hex, like 0xEB070194). Accepted as either, with the 0x prefix for hex. These are the recording’s own entity ids; subject/other in events, object references in Megalo values, parent and zone_id/occupant_id all use them.

JSONAdd the word json to any data verb. objects, events, seats, score and inside give an array of objects; megalo, variant, object and dump give one object. Missing values are null.

Verb reference

The playback verbs (film play, film seek, film camera, film stats, film extract, …) are on the Theater page. These are the data verbs.

film objects [filter...] [csv|json]

One row per object in the recording, filtered. Without at=/alive= the position and orientation columns are the object’s first recorded values (where it appeared); with a time they are the held values at that moment.

Filters (all must match):

KeyMeaning
type=Entity type name or tag path. Without * it is a substring test, so generic also matches generic_garbage; with * it is a glob. Names: biped item generic generic_garbage vehicle projectile weapon device (the object kinds), plus the non-object entities player megalo_team statborg and a few others. A tag path matches only when a map name source is available.
tag=Tag path glob (needs tag names; empty in script verbs).
label=Forge label text: exact (case-insensitive) unless it contains * (glob, anchored at both ends: ctf*, *_base). label=#12 matches the label-table index.
team=none, red, blue, green, orange, purple, gold (or yellow), brown, pink, or a number (-1 = none). Uses the replicated team, else the placement’s.
owner= (or player=)Substring of the owning player’s name (player bodies only).
slot=Owning player slot, 0–15.
alive=<time>Existed at that time. Also sets the time at which positions are evaluated and printed.
at=<time>The time at which near=/box= are tested and positions are printed (default: alive=’s time, else each object’s first position).
id=, parent=One object; objects attached to a parent id.
near=x,y,z,rPosition within radius r of a point, in world units.
box=x0,y0,z0,x1,y1,z1Position inside an axis-aligned box (corners in any order).
megalo=1A Megalo variable in the recording refers to this object.
zone=1The object has a boundary. zone=0 for the opposite.

Boundary dimensions: sphere uses w_or_r as the radius; cylinder uses w_or_r (radius), top and bottom; box uses width (w_or_r), length, top and bottom. Only objects the Forge placement can be matched to (items, generic objects, vehicles, weapons, devices) have placement columns; bodies and projectiles do not.

JSON rows are nested instead: id, id_hex, entity_type, type, def_wire, tag, first_tick, last_tick, destroyed_tick, position ([x,y,z]), parent, owner_slot, owner_name, megalo_ref, label, placement (an object, or null), mp (an object, or null) and zone_source. def_wire is the network tag reference; objects of the same kind share it, so it identifies a type even when there is no map to name it.

film inside and film near

film inside <id|filter...> [time | a..b] [r=R | cyl=r,top,bot | box=w,l,top,bot] [occupants=players|vehicles|all] [csv|json]
film near   <id> r=R [time | a..b] [occupants=...] [csv|json]

Who is inside a volume. The zone is one or more objects, chosen by id or by object filters (the same keys as film objects, e.g. label=zone_a). The volume is the object’s own boundary, moving with the object, unless you give one: r=R (sphere), cyl=radius,top,bottom or box=width,length,top,bottom place that shape at the object’s position and orientation, which is also how you test “within R of this object” for an object that has no boundary. film near is the sphere form and requires r=. An object with no boundary and no shape from you is skipped; if nothing matches you get an error.

The time argument decides the output:

  • A single time — a snapshot: rows with event = INSIDE, one per occupant inside at that tick.
  • A range a..b, or no time at all (the whole recording) — the zone is replayed tick by tick and every change is a row: ENTER when an occupant becomes inside, EXIT when it stops. A destroyed or not-yet-created zone is empty. Narrow the range on a long film.

Occupants: players (the default; player bodies), vehicles, or all (bodies, vehicles, weapons, items, generic objects, devices). Columns: tick,seconds,event,zone_id,zone_label,occupant_id,occupant_type,slot,name. slot and name identify the player owning a body and are empty for other occupants and for a body whose player could not be named.

A decimal object id is recognised as an id when it has more than six digits (real ids have ten); a short number is read as a time. Use the 0x form or id= to be unambiguous.

film inside label=zone_a 1:00..2:00

# illustrative
tick,seconds,event,zone_id,zone_label,occupant_id,occupant_type,slot,name

4006,66.767,EXIT,3943104916,zone_a,4013424645,biped,4,Alpha

film events [csv|json] [filter...]

The recording’s event channel, in tick order. Filters: type= (or kind=, or a bare word) — a number 0–71 or a name such as incident; player= (or name=) — substring of either party’s name; slot= — either party’s slot; from=, to= — time range.

Columns: tick,seconds,kind,name,subject,other,incident,incident_name,seat,subject_slot,subject_name,other_slot,other_name. subject and other are object ids (the unit acting or earning the incident, and the other party such as the victim or vehicle); the *_slot/*_name columns name the player when the object is a body that could be attributed. For incident events, incident is the numeric string id and incident_name its name when known. seat is the vehicle seat index for biped_board_vehicle, biped_enter_vehicle and biped_exit_vehicle, and empty otherwise.

Incident names include kill, death, suicide, assist, kill_betrayal, melee_kill, headshot_kill, splatter_kill, assassination_kill, finishing_move_kill, first_blood, flag_grabbed, flag_dropped, flag_scored, flag_reset, flag_recovered, round_over, game_over and multikill/spree medals; an id the program has no name for prints an empty name and the number. film seats [csv|json]

The time-aware roster: one row per segment of a player holding a slot. Columns: slot,identifier,name,team,data_team,from_tick,until_tick,left_tick,from_header,joined_in_progress. identifier is the player’s 16-hex-digit id; team and data_team are team indices (−1 = none); until_tick is when the segment ended (a reconfiguration, swap, removal or replacement) and left_tick when the player left the game; both are empty while still current. from_header is true for seats that come from the film header rather than a join update.

Use it to map a slot to a person at a given tick: the rows for one slot are consecutive segments, and a swap or a new player in the slot ends one and starts the next.

# illustrative
slot,identifier,name,team,data_team,from_tick,until_tick,left_tick,from_header,joined_in_progress
4,00A0000000000001,Alpha,0,0,0,,,true,false
6,00A0000000000002,Bravo,1,1,0,25006,,true,false
6,00A0000000000003,Charlie,1,1,25006,,,false,true

film score [csv|json]

The scoreboard’s change log: a row each time a score store changes. Columns: tick,seconds,statborg,is_team,owner_name,round_score,total_score,rounds_won,final. statborg is the store’s index: 0–15 are player slots, 16 and up are teams (index − 16 = team). owner_name is the player holding that slot at that tick (empty for teams). Blank cells mean that field was not stated. In JSON the unset fields are null.

film megalo ...

Only available for scripted (Megalo) gametypes; for any other engine type it answers that the game variant is not a Megalo script. film megalo reads the file itself, so it needs no film index.

FormOutput
film megalo / film megalo infoA text summary: trigger, action and condition counts, how many variables of each kind each scope declares and replicates, how many value changes were recorded, and the not-in-a-film list.
film megalo decls [csv|json]Every declared variable slot. Columns scope,kind,slot,priority,replicated,initial. priority is none, low, high or local; only low/high are replicated. Object-scope rows always show replicated=false.
film megalo vars [filter...] [csv|json]Every recorded change of every variable, time ordered. Columns tick,seconds,scope,owner,owner_name,kind,slot,value,text. The round clock and game state appear as rows with scope=game, owner=0, the game variable’s name in kind and the value in value/text. Filters: scope= (global player team object), kind= (number timer team player object), var= (or slot=; the variable index), owner= (a number is a slot / team index; anything else is a name substring), player= (same as owner=), from=, to=. Any filter drops the game rows.
film megalo at <time> [csv|json]Every variable’s value at one moment (columns as vars, tick = the time asked for), plus the game rows. JSON: {tick, seconds, variables: [...], game: [{name, value}]}.
film megalo get <scope> <owner> <kind> <slot> [csv|json]One variable’s series. owner is the player slot, the team index, or 0 for global. Columns tick,seconds,value,text. JSON: {scope, owner, kind, slot, points: [{tick, value, text}]}. Scope also accepts g p t o, kind accepts num n t obj. An error says the variable was not declared, not replicated, or never sent.

Reading value and text: a number is the number; a timer is seconds left in value, with text like 4s rate5 edge (a countdown changes once a second); a team or player variable is the team/slot index; an object variable is the object’s id (text is hex like 0xE9C70054) or -1/null when cleared. An object id from a variable can be passed straight to film object and shows up in film objects megalo=1.

Game variable names: current_state, game_finished, current_round, round_condition_flags, round_timer_seconds (the round clock, once a second), sudden_death_seconds, grace_period_seconds.

The JSON of film megalo vars is one object: declarations, coverage (how many replication messages were decoded cleanly), ticks, series (each {scope, owner, owner_name, kind, slot, points: [[tick, value], ...]}), game and not_in_film. In JSON a series carries one owner_name (the holder when it starts); use the CSV, or film seats, when the slot changes hands.

film variant [json] (alias film gametype)

The embedded game variant. Text form: title, author, engine, map id, team/round/respawn settings and a one-line Megalo summary. JSON keys: title, description, author, engine_type, engine, map_id, activity, game_mode, and, when the gametype decodes, teams_enabled, rounds, round_time_limit_min, early_victory_wins, sudden_death_s, grace_period_s, lives_per_round, respawn_time_s, suicide_penalty_s, betrayal_penalty_s, species, and megalo (the same declarations as film megalo decls json).

film dump [json]

Everything in one JSON document, for handing to another tool: {"schema": "hms-film-dump/1", "ticks": N, "variant": ..., "megalo": ..., "seats": [...], "events": [...], "score": [...], "objects": [...]}. megalo is the film megalo vars json object (or null for a non-Megalo gametype); the rest are the JSON forms of the verbs above. It does not include zone occupancy: compute that with film inside, or from the object tracks with your own geometry.

film highlight [csv|json]

The objects the Theater Highlight script objects switch outlines (see Theater), one row each: id,id_hex,category,name,label,team,entity_type,first_tick,destroyed_tick,shape,w_or_r,length,top,bottom. Categories: objective / flag, zone / hill, attached marker, script-spawned, labelled Forge, script variable, invisible / no model. From a script the tag path is not known, so the invisible category only catches invisible_* names; the Theater panel also uses the render model.

Cookbook

All of these assume the film is open and indexed (above). The Python helpers are in docs/examples: hms_cmd.py (queries a running app), zone_time.py and follow_zones.py.

Find all objects with a Forge label and their positions

film objects label=zone_a                 # where each appeared
film objects label=zone_a alive=3:00      # where each was at 3:00 (and only those existing then)
film objects label=ctf* type=generic json # a glob, as JSON
film objects label=#12                    # by label-table index
film object 3943104916                    # one object's full history, if it moves

The label column is empty for anything the gametype spawned at runtime. Use join_dist to check the position match: it should be a few hundredths of a world unit.

Who is inside zone Y over time (ENTER / EXIT)

film inside label=zone_y                      # the whole recording
film inside label=zone_y 5:00..6:00          # one window
film inside label=zone_y t23905               # who is inside at one tick
film inside label=zone_y occupants=vehicles
film inside label=marker r=10 0..3:00        # a 10-unit sphere round an object with no boundary

Time a player spends in or between zones

Get the ENTER/EXIT rows as CSV and pair them. The helper zone_time.py does the pairing, totals the time inside each zone per player, and prints the gap from leaving one zone to entering the next:

python3 -I hms_cmd.py match.mov "film inside label=zone_*" | python3 -I zone_time.py
# illustrative
Alpha: zone_a -> zone_b in 5.00s
Alpha spent 5.00s inside zone_a
Alpha spent 5.50s inside zone_b

Because positions are held between samples, a zone entry is detected on the tick the next position sample arrives, so times carry that granularity (see limits).

Track a Megalo variable for one player across slot changes

Run film index first, then filter by name, not slot: the name is resolved through the seats at each point’s tick, so the series follows the person even if they changed slot or someone else later took the slot.

film megalo decls                                  # what exists, and what is replicated
film megalo vars scope=player kind=number var=0 owner=alpha
film seats                                         # to see when the slot changed hands
film megalo vars scope=player owner=4              # by slot instead: whoever held slot 4

A variable’s meaning is decided by the gametype’s script, not by the film. Find it from the gametype itself, or by correlating the series with something you can see (a score change at the same tick, a position).

Follow an objective through a Megalo object variable

film megalo get team 1 object 1          # the object ids team.object[1] pointed at, over time
film object 4013686891                   # where that object was, in tick order
film objects megalo=1                    # every object a variable ever referred to

List kills, deaths and incidents in a time range

film events type=incident from=2:00 to=5:00
film events type=incident slot=4 json
film events type=weapon_reload player=alpha from=t6000 to=t7200
film events 14 from=t0 to=t3600           # a bare word or number is the type

Export everything as JSON for another tool

python3 -I hms_cmd.py match.mov "film dump json" > match.json
jq '.score[] | select(.final == true)' match.json
jq '[.objects[] | select(.label != null) | {id, label, position}]' match.json

Watch several labelled objects live

Use the follower (below): --watch-label is repeatable, so one process reports every enter and exit for all of them.

hms-app --film-follow match.temp --watch-label zone_a --watch-label zone_b --watch-radius 6 \
        2>follow.log | python3 -I follow_zones.py

The live follower: --film-follow

Reads a finished film, or a .temp the game is still writing, and prints what happens in it as a stream of events, one JSON object per line. It never opens a window, a GPU device or audio — the flag is handled before any of those exist — so it runs over SSH, as a service, or with no display. It is a separate mode from the script verbs: it keeps its own running state and reports changes, where the verbs answer questions about a finished recording.

hms-app --film-follow <film.temp|film.mov> [--emit json-lines|csv] [--poll-ms 1000] [--since T]
        [--watch-label NAME]... [--watch-id ID]... [--watch-radius R]
        [--objects] [--filter key=value]... [--all-events] [--clock]
        [--map cache.map] [--once] [--max-seconds N]
FlagMeaning
<path>The film or .temp. It may not exist yet: the follower prints waiting: ... on stderr and keeps polling.
--emitjson-lines (default; jsonl and json also accepted) or csv. CSV has the header id,tick,seconds,type,data; data is the whole event as a quoted JSON string.
--poll-ms NHow often the file’s size and modification time are checked (default 1000, minimum 20). The file is only re-read when one of them changed.
--since TSuppress events with a tick at or before T (seconds, mm:ss or t1234). See resuming.
--watch-label NAMEWatch the objects with that Forge label for occupants entering and leaving (zone_enter / zone_exit). Repeatable. Matched exactly, ignoring case; no globs here.
--watch-id IDThe same for one object id (decimal or 0x hex). Repeatable.
--watch-radius RFor a watched object that has no boundary of its own, use a sphere of radius R around it. A watched object with neither a boundary nor --watch-radius reports nothing.
--objectsAlso report object_spawn / object_delete (not for projectiles).
--filter key=valueWith --objects: only for objects matching (the same keys as film objects; repeatable). It does not affect zone events.
--all-eventsReport every event-channel event as event, not just incident.
--clockInclude the once-a-second round clock and the sudden-death and grace-period timers as game events (off by default; they are noisy).
--map cache.mapTurn object definitions into tag paths for the tag field. The only use of a map.
--onceProcess the file as it is now and exit.
--max-seconds NExit after about N seconds.

Standard output carries only events. Status goes to standard error, one line per file change: refresh: 12000 records (1500 new), 8 events, 11.2 ms wall, 10.9 ms cpu. A bad argument prints the reason and usage and exits with code 2. If the program reading the pipe goes away, the follower exits with code 0.

Following a recording the game is still writing

  • The game rewrites the .temp roughly every 15 seconds, each time the same stream with more records at the end. That is a limit on freshness no reader can beat: events appear in batches, up to about 15 seconds after they happened in the match.
  • The follower reads only complete records, decodes only the ones it has not seen, and keeps all state between refreshes, so the cost of a refresh depends on what is new.
  • Nothing is printed until the file holds 256 records (about four seconds of play); at that point everything from the start is reported in one burst.
  • If the file is replaced by a different match, or becomes shorter, a reset event is printed and following starts over (a consumer should discard its state).
  • When the match ends MCC finalises the recording and renames the .temp. The follower does not chase the new name: it keeps polling the old path and prints nothing. Stop it, and run it once more with --once on the finished file if you want the tail (use --since to skip what you have).
  • If the file cannot be opened or parsed at the moment of a poll (the game is mid-write), the follower prints waiting: ... on stderr and tries again on the next poll; nothing is lost.

Running it in the background and piping it

# write the stream to a file, status to a log
hms-app --film-follow match.temp --objects --watch-label zone_a --watch-radius 6 \
        > events.jsonl 2> follow.log &

# or pipe it straight into a consumer
hms-app --film-follow match.temp --watch-label zone_a --watch-radius 6 2>/dev/null | python3 -I consumer.py

The follower flushes after every batch of events, so a consumer reading line by line sees them as they are produced. On Windows, run it from a terminal and redirect or pipe the output. With no display (SSH, a service) nothing else is needed: the --film-follow mode does not touch the graphics stack.

De-duplication and resuming with --since

Every event has an id of the form <tick>-<n> (n counts events within a tick). The stream is deterministic: the events for the first part of a file are exactly the beginning of the events for the whole file, however the file was chunked into refreshes. So an id never repeats within a run, and a restarted follower produces the same ids for the same events. To resume after a restart, pass the tick you last handled; the follower re-decodes from the start (a cold start is about a second on a long film) and suppresses events at or before it:

hms-app --film-follow match.temp --since t24000 --watch-label zone_a --watch-radius 6

Because --since drops events with a tick at or before the value, pass the last tick minus one and skip ids you have already stored, if events in the final tick may not all have been written when you stopped.

Within a tick, events come in the order roster changes, events and incidents, destroys, entity-driven events (score, Megalo, spawns), then zone changes. Watched objects are registered when they are created, so a watch started on a film that already contains the object still works (the follower decodes from the start).

Polling and CPU cost

Measured on a 47-minute, 150 MB film: re-reading and framing the file is about 55 ms; decoding 1,500 new records (25 seconds of play) about 10 ms; a cold start over the whole film about 1.2 seconds. Memory is the follower’s per-object state only. At the default 1 s poll the follower only looks at the file’s metadata unless the game has rewritten it, so it idles at essentially zero CPU between the game’s writes.

Generic consumers

Shell: print a line whenever any watched object gets an enter or exit:

hms-app --film-follow match.temp --watch-label zone_a --watch-label zone_b --watch-radius 6 2>/dev/null |
  jq -r --unbuffered 'select(.type=="zone_enter" or .type=="zone_exit")
                      | "\(.seconds)s  \(.name // .occupant_id)  \(.type)  \(.zone_label // .zone_id)"'

Python: the same, plus the time each occupant spent inside each zone (examples/follow_zones.py, run as python3 -I follow_zones.py):

import json, sys

seen, since, total = set(), {}, {}
for line in sys.stdin:
    e = json.loads(line)
    if e["id"] in seen:                       # de-duplicate by event id
        continue
    seen.add(e["id"])
    if e["type"] == "reset":                  # a different match: forget everything
        seen.clear(); since.clear(); total.clear()
    elif e["type"] in ("zone_enter", "zone_exit"):
        zone = e["zone_label"] or e["zone_id"]
        who = e["name"] or f'{e["occupant_type"]} {e["occupant_id"]}'
        key = (e["zone_id"], e["occupant_id"])
        print(f'{e["seconds"]:9.2f}s  {who:<16} {e["type"][5:]:<5} {zone}', flush=True)
        if e["type"] == "zone_enter":
            since[key] = e["seconds"]
        elif key in since:
            total[(who, zone)] = total.get((who, zone), 0.0) + e["seconds"] - since.pop(key)

An occupant still inside when you stop has not been counted: add now - since[key] for the open entries at exit if you need it. The same approach works for any other event type: filter on type, key the state by the fields that identify what you are tracking, and de-duplicate on id.

Limits and gotchas

  • Position sampling is sparse. A body’s position is only sent on some ticks and HMS holds the last sample until the next. A fast player can cross a small zone between two samples and never be seen inside it; an ENTER or EXIT can lag the true crossing until the next sample. Larger zones and slower objects are reliable. Vehicles and bodies share this.
  • Labels are matched by position. The stream does not state an entity’s Forge label; HMS finds the variant placement within a quarter of a world unit of the entity’s first position. Check join_dist. Two placements stacked at the same point are ambiguous (the nearest wins). Anything spawned by the gametype has no label.
  • Box zones are approximate. Sphere and cylinder tests are exact. For a box, HMS treats width and length as full extents (the numbers the Forge UI shows); the engine’s own test was not located, so the box could be half that size. Prefer sphere or cylinder zones where you can, or confirm a box against a known event (a score at a known tick).
  • Tag names need a map. Without --map (follower) the tag field is empty; script verbs always leave it empty. def_wire (in JSON and in film object) and the placement columns identify the type instead.
  • Per-object Megalo variables are not recorded, and neither are variables with network priority none or local. A variable you cannot find in film megalo vars may simply not be replicated; film megalo decls says which are.
  • Slots are not people. Key player data by name through film seats (or the *_name columns), not by slot, whenever players can swap or join late.
  • The kill feed is the recorder’s. See what is not in a recording.
  • A film started mid-match carries a Megalo variable only from its first update; before that its value is unknown, not zero.
  • Player bodies in an in-progress recording are bound to players by a different route than in a finished film (there is no author record yet), so on some clips fewer bodies have names until the film is finalised.
  • Paths with spaces do not work in the script grammar (no quoting). --film-follow takes its path as one command-line argument, so it is fine there.
