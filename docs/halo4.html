Halo 4

Halo 4 maps from MCC can be opened, and their Forge map variants can be edited with the same tools as Reach (select, move, rotate, place from the palette, duplicate, delete, undo, object properties) and saved. The encoder reproduces every shipped variant byte-for-byte and an HMS-saved variant loads in MCC, so File ▸ Save writes the open file in place and Save As writes a new one.

How to use it

  • Halo 4 caches are detected from <MCC>\halo4\maps and from Halo 4 Workshop items, and appear in the map picker's Halo 4 group (only shown when at least one exists). Load one like any other map.
  • The status line reads Halo 4: <map> — N draws / N tris, N objects + N map-variant objects (editor scene), N textures…
  • File ▸ Open .mvar… accepts Halo 4 variants (the game's halo4\map_variants and hopper_map_variants folders are quick links in the browser, and your own saves are under …\MCC\LocalFiles\<XUID>\Halo4\Map). The variant's base map is loaded automatically, the camera lands at the variant's initial spawn, and its objects become editable objects in the Objects list and the viewport. Variant titles and descriptions that the game stores as localisation keys ($h4_mvar_…) are resolved to their English display names from MCC's localisation tables, so the browser shows "Settler" rather than the key.
  • The Palette panel lists the map's Forge palette (the same 17 categories the game's Forge menu shows, localised names; the superforge-only block set is marked). Drag a row into the viewport to place it; the placed object gets the game's own defaults for that piece (physics, spawn time, boundary shape, spare clips) and saves like any other object. Selecting a row shows the piece in the 3D preview beside the list, built through the same object path, materials and map lighting the viewport uses, so a previewed block looks like the same block in the scene (a row whose object has no render model would show the editor's marker cube, exactly as it draws in the viewport - every row of the shipped palettes has a model); right-drag orbits it, the scroll wheel zooms, and dragging it out places the piece.
  • File ▸ Save writes the edited objects back into the open .mvar; Save As… writes a new one. Saving into the game’s halo4\map_variants folder is supported — that is the folder MCC’s Custom Games list scans; only hopper_map_variants (matchmaking) is refused, because the game never lists a file saved there. A save check window lists anything the file cannot hold: objects outside the variant bounds (Halo 4 has no way to encode those — Save As anyway clamps them to the edge), objects past the 651 slots, and objects with no palette entry. The budget and a palette entry's Maximum Allowed are not checked: the game recomputes the spend, restores the map's own sandbox budget and spawns the extras anyway, so HMS simply writes a maximum that covers what the pieces cost.
  • Headless rendering works the same way: HMS_MAP=ca_forge_ravine HMS_SHOT=ravine.png ./hms-app, with HMS_MVAR accepting Halo 4 variants only.

What works

  • Vehicle attachments render: a variant that carries a child object (the Warthog turrets, the Wraith mortar, the Scorpion cannon, the Revenant main gun) draws it posed on the parent’s marker, with its own materials.
  • Level geometry with diffuse textures (all common compressed formats).
  • Baked lightmaps and the baked sun direction and colour, atmospheric fog, the map's exposure range and bloom settings.
  • Material routing (opaque, alpha-tested, blended, additive), a shipped-shader lighting model, and the sky.
  • Scenario objects (the level's own placed objects) in their bind pose.
  • Reading shipped and user map variants and drawing their Forge objects (all shipped Halo 4 variants decode, and every one of the 388 shipped files re-encodes byte-identical).
  • Editing: click / box-select with the selection outline, G / R modal transforms and the gizmo, Shift+D duplicate and arrays, Delete, Ctrl+Z / Ctrl+Y, drag-and-drop placement from the palette, and every script verb (place, moveto, rotate, dup, delete, set, get, save as). Marker-only pieces (spawn zones, kill areas, trait zones: objects without a render model) draw as a translucent cube so they can be selected and moved.
  • Object panel for a Halo 4 object: quota / variant (with the palette name), team and colour (with the hover preview), the read-only object type, spawn sequence (−100 … 100, with the size the scale-label rule gives next to it) and spawn time (named as in the game's Forge menu), up to four gametype labels, parent, placement flags (plus the two raw Halo 4 bits), boundary shape with values shown in world units, the type-specific extras (spare clips, teleporter channel / passability, trait zone, ordnance tables), user data, the Forge lock, a collapsed raw group (the record's variant-object-scale field — see below — and the slot flags), and position / rotation. A multi-selection fans every edit out to the whole selection, as for Reach.
  • Collision and physics hulls. View ▸ Overlays ▸ Collision (selected) draws the selected object's collision model (coll) in cyan and Physics (selected) its physics model (phmo) in orange, the same two rows Reach has. Halo 4 keeps the collision BSP in a paged resource rather than in the tag, and its rigid-body shapes (boxes, capsules, spheres, convex polyhedra, lists and MOPP containers) are read straight out of the cache; each hull is posed by the node it belongs to, so a vehicle's wheels and turrets sit where they should. Script: collision on|off, physics on|off.
  • Superforge (hidden) blocks. The bb_* pieces of the map's hidden Forge palette draw nothing in game — their render model is a 0.1 wu placeholder and their real shape is their physics hull. HMS overlays that hull in orange and makes the block behave like an object of that size: click it, box-select it, see its wireframe, and snap or array copies flush against its faces. The same View ▸ Show hidden-block physics hulls switch (on by default) controls it.
  • The Halo 4 parser is pure Rust, so the native library is not needed for Halo 4 maps.

Scaling

One thing scales a Halo 4 Forge object on screen, and one thing looks like it should but does not:

  • The scale-label gametype rule, as in Reach: a scaling Forge gametype (a Megalo script) reads the spawn sequence of every object carrying the scale label and calls the engine's set-scale at runtime. Halo 4's "spawn sequence" (the Forge menu name; Megalo object.user_data) is the signed −100 … 100 number next to "user data" in the object menu. The editor applies this through the same SCALED pseudo-flag and convention picker as Reach (X330 by default, X47 also used by the author's gametypes) — set the label, raise the spawn sequence, and the object grows; the size the rule gives is shown next to the spawn sequence, get prints it as gametype_scale, and objects scaled this way show [scaled] in the Objects list. The global Scaled objects switch still turns it off.
  • The record's own variant-object-scale field — stored, not drawn. Unlike Reach, a Halo 4 object record carries a 6-bit scale (64 steps over 0 … 10) that the game decodes, keeps across its own saves and copies into the spawned object — and then draws the object at its normal size anyway. The name is the engine's own: the Halo 4 Editing Kit's halo4_tag_test.exe keeps its debug strings, and its record decoder reads the field as variant-object-scale (min 0, max 10, 6 bits), the lock as locked-from-forge-editing, and its object_new asserts data->scale>0.0f on the placement field the value is copied into; the H2A kit is byte-for-byte the same chain (docs/halo4_mvar_layout.md section 11d). This was settled by test and by the shipped maps: rewriting the field on every object of a whole map changed nothing in MCC Forge while the game's session autosave carried the values, and the shipped files themselves store Exile's Scorpion at ×0.565, Monolith's two man cannons at ×0.73 / ×0.89, Vortex's dominion shields at ×2.18 and every plain object at ×1.048 — all of them drawn at normal size in the game (details in docs/halo4_mvar_layout.md section 11c). The editor therefore keeps the field only so files round-trip: it sits in the Object panel's collapsed raw group as "variant-object-scale", get prints it as variant_object_scale, and set <datum> scale <0..10> still writes it, but it never changes what the editor draws or marks.

Verification status

  • Saving is confirmed in the game. The encoder reproduces every shipped variant byte-for-byte (including the chunk hash), and an HMS-saved variant has been loaded in MCC. Save writes the open file in place; Save As writes a new one.
  • Boundary shape sizes (stored in 1/256 world units) and the two extra placement bits are decoded and written back faithfully but their in-game meaning is unverified. The "user data" byte and the Forge lock were traced in the game code (docs/halo4_mvar_layout.md section 11). The record's variant-object-scale field is verified not to be drawn by MCC (section 11c, above): the game stores and copies it, and the static trace of halo4.dll — confirmed with the Editing Kit's named build and the H2A kit, none of which has a gate, a global or a compiled-out block on the path (section 11d) — follows it all the way into the GPU node matrices, yet two in-game tests and the shipped maps show objects at their normal size — so treat it as a raw field; the scale-label rule is the mechanism that works.
  • Change colours apply to the Halo 4 families that sample a colour-change mask, from the multiplayer globals team palette (explicit colour, then team, then neutral). Covenant hulls take no change colour in the engine at all: their colour comes from a view-angle ramp in the srf_char_cov family. The secondary, tertiary and quaternary colours are unported (no shipped Forge material samples them), and srf_char_blinn still uses the generic fallback, so UNSC hulls such as the Scorpion are not shader-exact.

Not supported yet

  • Picking the map's own scenario objects (they draw but are not selectable). The Reach-only SCALED / SHADOW flags and the playable-space (BSP) warning do not apply to Halo 4 objects.
  • Normal and specular maps, skinned/animated poses, particles, decals, decorators (grass), camera stand-off. (Collision and physics hulls are read and can be overlaid — see above — but nothing collides against them: the editor's raycasts still use the render mesh.)
  • Variants of the newer version 51 format are refused.

Known issues

  • Lighting uses the game's own baked lightmaps (two-lobe direction/intensity atlases, sun visibility and the baked sun), a Blinn/Phong material model with normal and control maps, cube reflections, fog and the filmic tone curve, all derived from the shipped shaders. Transparent surfaces (glass, water, foam), runtime lights and colour grading are not finished, so some surfaces can still look flat or off in tone.
  • The default camera on campaign maps frames every BSP at once and can start outside the level. Use the object list or fly manually.
  • Some instanced geometry may be mirrored or rotated incorrectly on asymmetric instances.
  • Object boundary shape sizes and a few placement flags are decoded but not yet verified against the game (see above).
  • A shipped variant can store an object type that differs from its palette entry (stale authoring); the save check reports these and writes them as they are.

Fallback switches

If a Halo 4 map fails to render, these environment variables turn parts of the pipeline off so the rest can still be viewed: HMS_H4_LIGHTMAP=0 (flat lighting), HMS_H4_SHADING=0 (flat diffuse), HMS_H4_NOTEX=1, HMS_H4_NOOBJ=1, HMS_H4_NOSKY=1.

Maps tested

Ravine (ca_forge_ravine), Haven (wraparound), Erosion (ca_forge_erosion), Impact (ca_forge_bonanza), Forge Island (dlc_forge_island), plus several campaign and Spartan Ops caches; variants including Settler (on Ravine) and Grifball Court (on Erosion).
