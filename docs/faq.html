FAQ / troubleshooting

"No maps detected (is MCC/Halo Reach installed via Steam?)"

The app could not find an MCC install. Check, in order:

  1. MCC is installed through Steam and the Halo: Reach content is downloaded (Steam ▸ MCC ▸ Properties ▸ DLC). The app needs …\Halo The Master Chief Collection\haloreach\maps\*.map.
  2. The Steam library is in a normal place. Libraries on other drives are found through Steam's libraryfolders.vdf; on Linux the Steam root must be one of ~/.local/share/Steam, ~/.steam/steam, ~/.steam/root, the Flatpak location or $XDG_DATA_HOME/Steam.
  3. Otherwise tell the app where the game is with HMS_MCC_DIRS — the MCC folder, a haloreach folder or a maps folder, several separated by ;: 
    HMS_MCC_DIRS="/path/to/SteamLibrary/steamapps/common/Halo The Master Chief Collection" ./hms-app
    On Windows set it in the same terminal before starting hms-app.exe, or create a shortcut / batch file that sets it.
  4. Xbox / Microsoft Store installs are probed only when no Steam copy exists, and only in the default XboxGames / ModifiableWindowsApps locations; use HMS_MCC_DIRS for anything else.

hms-app --dump-maps prints exactly what was found, which is the quickest way to debug this.

My Workshop map shows up under Built-in (or the other way round)

The grouping is purely by folder: anything under steamapps\workshop\ is Modded, anything inside the game's own maps folder is Built-in — including Anniversary maps and copies you placed there yourself. A Workshop item is only listed if its ModInfo.json declares a Halo: Reach or Halo 4 engine.

Maps are listed by file name, not by their in-game name

Correct — the picker shows the scenario stem (45_aftship is Zealot, 50_panopticon is Boardwalk). See the table on Maps & variants.

The app does not start, or says "no wgpu adapter"

No usable GPU driver was found. You need Vulkan (Linux) or DirectX 12 / Vulkan (Windows) drivers. As a last resort the software rasteriser is used — on Linux install lavapipe / vulkan-swrast (mesa-vulkan-drivers on Debian/Ubuntu); on Windows WARP ships with DirectX 12. HMS_SOFTWARE_GPU=1 forces the software path for testing. The app prints adapter: <name> (<type>, <backend>) to the terminal at start so you can see which device it picked; it prefers discrete over integrated GPUs automatically.

How much memory does it need?

Loading Forge World peaks at roughly 4.5 GB while textures are decoded and settles to about 1 GB afterwards. Smaller maps need less. There is no explicit RAM check, so on a machine with 4 GB or less the load may fail or swap heavily.

Loading Forge World is slow the first time

Expect a few seconds on a fast machine (timings are written to hms_load.log next to the executable). Reload forge rebuilds only the Forge objects and is much faster than a full Reload.

My variant opens but shows "N unresolved" or "0/N objects resolved"

Each object in a variant refers to an entry of the base map's Forge palette. If the variant was made for a different map (or a modded map with a different palette) those references cannot be matched. The app loads the base map automatically by the map id stored in the file; if that map is not installed the variant is drawn on whatever is loaded and most objects will be unresolved. Unresolved objects are kept in the file on save; they are simply not displayed. hms_mvar_diag.txt next to the executable and hms-app --resolve-mvar <map> <file.mvar> show the details.

Does Save make a backup?

No. File ▸ Save overwrites the open .mvar in place. Use Save As… or copy the file first. Never save over a variant while MCC has it open. See Saving for exactly what is rewritten.

Where does MCC keep my Forge saves?

%USERPROFILE%\AppData\LocalLow\MCC\LocalFiles\<XUID>\HaloReach\Map\ on Windows, and the same path inside the Proton prefix on Linux (…/steamapps/compatdata/976730/pfx/drive_c/users/steamuser/AppData/LocalLow/MCC/LocalFiles/…). The variant browser lists them under Game as 👤 HaloReach · <profile>. If your LocalFiles is elsewhere, set HMS_MCC_LOCALFILES.

I placed objects but the count did not change / they were not saved

A variant has 651 slots and objects the app cannot display still occupy theirs. When the file is full, new objects cannot be written; the status line says how many had no free slot. New objects whose palette entry cannot be resolved on this map are also dropped from the save (again reported in the status line).

The arrow keys / PageUp / [ ] do not move my object

In v0.1.0 those nudge keys only drive a legacy path and do not move variant objects, even though the in-app shortcut list still mentions them. Use G, lock an axis with X/Y/Z, type the distance and press Enter, or edit the position fields in the Object panel.

Can it edit the live game / place objects while MCC is running?

Not in the released builds. Halo Map Studio works entirely on files: it reads the game's map caches and reads/writes .mvar variants. Load the saved variant in the game's Forge to see it in-game.

The image looks different from the game

See How accurate is the renderer? for what is reproduced and the known gaps. Lighting sliders in Settings are reset to the map's values with Reset all; make sure Path-traced lighting and Real-time lighting (probe GI) are off when you want the stock look.

It crashed — what should I report?

Attach hms_crash.log (written next to the executable on a panic), the terminal output including the adapter: line, your OS and GPU, and the map / variant you were using. Please do not attach the game's .map files.

Linux specifics

  • Keep libhalomapstudio.so next to hms-app; the app loads it at start and prints a warning if it cannot.
  • Settings live in $XDG_DATA_HOME/HaloMapStudio or ~/.local/share/HaloMapStudio.
  • Mouse capture while flying: on Wayland the cursor is locked in place; on X11 it is confined to the window instead (X11 refuses pointer locking), which is normal.
  • The Proton install of MCC is an ordinary Steam library entry; no Wine tricks are needed to read the maps.
